## What the backlog says

> `WorkflowFuncPool` is `PoolSize: 3` per instance. Any blocking node caps a run at three concurrent
> branches; one 90-second LLM or remote call holds a third of that run's capacity. Make it configurable
> globally and per-schema, and make sure the remote transport (B-02) never holds a worker while awaiting
> a callback.

## Premise status

The code fact is **confirmed by reading**: `internal/actors/workflow_func_pool.go:40` sets
`PoolSize: 3` literally inside `WorkflowFuncPool.Init`, with no config seam. Re-read during dossier
creation.

The *behavioural* claim — that three blocking nodes cap a run at three concurrent branches, and that a
long LLM call holds a third of a run's capacity — is UNVERIFIED. Stage 1 must run
`fuse-premise-verifier` and demonstrate it; a hardcoded constant is not by itself a defect.

**This task splits, and the split matters.** The configurable-pool-size half is buildable today. The
"remote transport never holds a worker while awaiting a callback" half **cannot be built or tested
before B-01 and B-02** — there is no remote transport: `pkg/transport/type.go` declares HTTP and gRPC
and implements neither. Treat the second half as a constraint A-10 *writes down* for B-02 to satisfy,
not as work A-10 delivers. Say so in the plan rather than discovering it at implementation time.

## Route

Standard pipeline for the first half; the second half routes into B-01.

1. `fuse-premise-verifier` — the behavioural claim only: does a run with more than three concurrent
   blocking branches serialise at three? The hardcoded constant needs no verification.
2. `fuse-implementation-planner` — with the verdict. It must scope A-10 to the configurable half and
   record the non-blocking requirement as a **constraint on B-02**, with a named place it is written
   down (the B-01 spec is the obvious home).
3. `fuse-go-implementer`, then `fuse-code-reviewer`.

Run `go test -race ./internal/... ./pkg/...` for this one — it is actor/concurrency work and **`-race`
is in no gate** (no `-race` in the Makefile or `.github/workflows/ci.yml`).

## Out of scope

- **B-02** owns making the remote transport real and releasing the worker on
  `NewFunctionResultAsync()`. A-10 does not implement a transport to prove a point.
- **A-09** owns payload cost; a bigger pool makes A-09 worse in absolute terms but is not its fix.
- Rate limiting and concurrency *scopes* are **ADR-0016**'s territory and are not this task — do not
  build a limiter here.

## Decisions

Neither an ADR nor a SpecKit spec for the configurable half — it is a config knob with a default that
preserves current behaviour. Interacts with **ADR-0016** (Multi-scope concurrency control and rate
limiting), which is the record for how concurrency is bounded, and **ADR-0002** (Ergo actor model for
workflow execution), which is why the pool exists at all. The non-blocking half is a **B-01 spec
decision** (its item 3, ack semantics, and the async path generally), not an A-10 decision.

A new environment variable is a public deployment surface: document it wherever config is documented.
There is no CHANGELOG file in this repo.
