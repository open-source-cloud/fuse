## What the backlog says

> `replayJournalEntries` calls `SetResultFor`, which appends. `LoadFrom` sets `lastPersisted = seq`, so
> replay duplicates get fresh sequences and are persisted at the end of `Init`. The journal grows by a
> full copy of completed steps every restart and `trace_builder.go:BuildTrace` renders each step N+1
> times after N restarts.
>
> Suppress journaling during replay via a replay flag. It compounds, and it corrupts the trace — the
> thing you sell.

## Premise status

UNVERIFIED by execution — stage 1 must run `fuse-premise-verifier` before any code. One clause was READ
as contradicted, per the skill pack's Traps:

- **Journal growth: stands (read).** `SetResultFor` appends; `LoadFrom` sets `lastPersisted = seq`, so
  replay duplicates take fresh sequences and flush at the end of `Init`.
- **Trace rendering: contradicted (read).** `internal/workflow/trace_builder.go:10` appends a step row
  **only** on `JournalStepStarted`, and `replayJournalEntries` (`internal/workflow/workflow.go:199`)
  does not append a journal entry for that type — it only calls `auditLog.NewEntry`. It is
  `JournalStepCompleted` that routes into `SetResultFor`. So a duplicated `step:completed` finds the
  existing `stepIdx[execID]` and **mutates that row in place**: `CompletedAt`/`Duration` recomputed
  against the *replay* timestamp, `Status` forced back to `completed`. **Corruption in place, not
  N+1 duplication.** Re-scope the entry to say that.

**Hard constraint on the fix, from the same read:** `internal/workflow/workflow.go:428`
(`w.aggregatedOutput.Set(entry.FunctionNodeID, result.Output.Data)`) inside `SetResultFor` is the only
thing rebuilding aggregated output during replay. **Gate the append; never skip the call.** A replay
flag that short-circuits `SetResultFor` wholesale silently empties the data plane on every resume.

## Route

Standard pipeline, no inversion. Small task; skip stage 2 research unless the verifier's verdict opens a
question the plan would otherwise guess at.

1. `fuse-premise-verifier` — sub-claims split: (i) does the journal grow by a full copy of completed
   steps per restart? (ii) does `BuildTrace` render N+1 rows, or mutate one row in place? Hand it the
   Traps entry verbatim so it tests the replacement claim, not only the written one.
2. `fuse-implementation-planner` — with the verdict. Must state how the replay flag preserves the
   `aggregatedOutput.Set` call.
3. `fuse-go-implementer`, then `fuse-code-reviewer`.

Replay tests are order- and timing-sensitive — `go clean -testcache` before trusting a green run.

## Decisions

Neither an ADR nor a SpecKit spec — this is a bug fix with a sharp constraint. It does, however, correct
behaviour that **ADR-0010** (Durable execution via an append-only journal) describes, and the trace it
repairs is **ADR-0020**'s (Observability: metrics, tracing, execution traces) persisted execution trace.
No public API change.
