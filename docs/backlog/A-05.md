## What the backlog says

> `workflows` has `schema_id` and no version column; `postgres/workflow.go:Get → loadGraph(ctx,
> schemaID)` reads the *active* definition, so a run recovered after an edit replays against current
> topology. Rollback writes a new active version, silently swapping in-flight runs, unrecorded in their
> journals.
>
> `FindByIDAndVersion` already exists on the service and both repositories — the run just never records
> where it started. Add `schema_version` to `workflows`, record and journal it at trigger, resolve
> `loadGraph` by `(schemaID, version)`, and leave in-flight runs alone on activate and rollback.

## Premise status

UNVERIFIED — stage 1 must run `fuse-premise-verifier` before any code. Nobody has executed a test that
recovers a run after an edit and shows it replaying against the current topology.

One READ refinement from F-01.3 this session that sharpens the target: `SetActiveVersion`
(`internal/repositories/graph_memory.go:158-163`) and `Rollback`
(`internal/services/graph_service.go:154-161`) both build a **new** `Graph`. So activate and rollback do
**not** rewrite a live in-memory run's topology in place — they leave it on a **stale** graph instead.
The swap the entry describes is therefore a property of the **durable reload** path
(`postgres/workflow.go:Get → loadGraph`), not of the live object. Stage 1 should verify the durable
half directly under `DB_DRIVER=postgres` and not be misled by memory-driver behaviour.

## Route

Standard pipeline; the decision record precedes implementation.

1. `fuse-premise-verifier` — sub-claims: (i) `workflows` has no version column; (ii) a run recovered
   under Postgres after an edit resolves the *active* graph, not the one it started on; (iii) rollback
   changes what an in-flight run replays against. Run it against a real Postgres.
2. `fuse-implementation-planner` — with the verdict. Must cover the migration, backfill for existing
   `workflows` rows, and the journal entry recording the pinned version at trigger.
3. `write-adr` — see Decisions.
4. `fuse-go-implementer`, then `fuse-code-reviewer`.

## Done when

The backlog states the work as an imperative list; restated as assertions.

- [ ] `workflows` carries a `schema_version` column, added by a migration `fuse migrate` applies.
- [ ] The version is recorded **and journalled** at trigger, so it survives a rebuild from the journal.
- [ ] `loadGraph` resolves by `(schemaID, version)`, not by "active".
- [ ] Activating a new version leaves in-flight runs on the version they started with.
- [ ] Rollback leaves in-flight runs on the version they started with.
- [ ] Both drivers behave identically; verified with `make test-functional` and `DB_POSTGRES_DSN`
      exported (it **skips silently** without it — Traps).
- [ ] `make lint && make build && make test` green.

## Decisions

**ADR expected.** The backlog does not say so in the entry, but the delivery pipeline's stage-3 table
lists "A-05 version pinning" as ADR-weight: it is a data-model decision that is costly to reverse.
Interacts with **ADR-0014** (Immutable schema versioning with active-version pointer) — `Accepted` and
therefore immutable, so this is a *new* ADR that extends it to running instances, not an edit — and
with **ADR-0010** (Durable execution via an append-only journal), since the pinned version has to be
journalled. Next free number is 0035 (coordinate with A-03, A-04, A-11; numbers are never reused).

Schema migration → migration path required. No CHANGELOG file exists in this repo; raise it with the
maintainer rather than inventing one.
