## What the backlog says

> Iteration bookkeeping lives in `forEachStates`/`iterThreadToForEach` — plain Go maps, never
> reconstructed — so an in-flight ForEach does not survive a restart, even though the journal already
> writes four foreach entry types and reads none. Same class of bug as A-02.
>
> Worse: `spawnForEachBatch` dispatches straight to the function pool, **bypassing system-function
> interception**, so `system/subworkflow`, `system/sleep` and `system/wait` inside a ForEach body hit
> the no-op placeholder, return success instantly, and silently do nothing. Silent wrong answers are
> worse than crashes. If the real fix is large, ship schema validation that **rejects** those functions
> inside a ForEach body in the meantime.

## Blocking prerequisite — verify this first, under real Postgres

Recorded in the skill pack's Traps, **not** in the backlog entry, and re-confirmed by reading while
this dossier was written:

- `internal/workflow/journal.go:42-49` declares four `foreach:*` entry types.
- `internal/repositories/postgres/migrations/000001_create_tables.up.sql:12` creates
  `journal_entry_type` with **13** values and **no `foreach:*` among them**; the only later widening is
  `000004_add_manual_retry_journal_type.up.sql`, which adds `step:manual-retry` alone. Fourteen values
  total.
- `postgres/journal.go:84` inserts `string(entry.Type)` directly.

*Inferred, not executed:* under `DB_DRIVER=postgres`, inserting a `foreach:*` entry must be rejected by
the enum, so the journal flush after a `system/foreach` node starts fails the whole transaction — and
because `persistJournal` deliberately does not `MarkPersisted` on error, that run's journal freezes at
the last pre-foreach sequence, forever.

**Verify this under a real Postgres as the very first step of C-08.** Nothing about ForEach replay is
observable until it holds, and if it holds, the `ALTER TYPE … ADD VALUE` migration ships first (pattern:
`000004`; note enum migrations are effectively irreversible — `000004`'s down file is a comment
explaining why).

```bash
psql "$DB_POSTGRES_DSN" -c "SELECT unnest(enum_range(NULL::journal_entry_type));"   # expect 14, no foreach:*
```

## Premise status

**UNVERIFIED by execution; both backlog clauses READ-confirmed, and a third defect found by reading.**

- *State does not survive.* `forEachStates map[string]*ForEachState` and
  `iterThreadToForEach map[uint16]string` (`workflow_handler.go:97-100`) are re-initialised to empty in
  `Init` (`:118-119`) and never reconstructed.
- *Interception bypass.* `spawnForEachBatch` (`workflow_handler.go:1043-1046`) sends the
  `RunFunctionAction` straight to `WorkflowFuncPoolName`, so the switch at `:675-688` never runs.
  **A second, unlisted instance of the same bypass:** the `ActionRetryFunction` branch at
  `workflow_handler.go:658-668` also `SendAfter`s directly to the pool. The backlog names only the
  first.
- *Third defect, from the pack:* `StartForEachIteration` (`foreach.go:42-51`) creates the dynamic
  thread with `threads.New` but journals `foreach:iteration:started`, **not `thread:created`** — so on
  resume the iteration thread does not exist in `w.threads` while its `step:started` still yields a
  pending thread. `Next` then calls `w.threads.Get(threadID)` and immediately `CurrentExecID()` with no
  nil check (`workflow.go:310-311`) — a nil-pointer panic. This is the same unguarded shape as **V-c**;
  V-c is at `workflow.go:312-314` on `graph.FindNode` and is separately unfiled.

## Route

1. **Enum check under real Postgres** (see above) — before anything else.
2. `fuse-premise-verifier` — sub-claims, in order: (a) a `foreach:*` journal insert is rejected under
   Postgres; (b) `system/sleep`/`system/wait`/`system/subworkflow` inside a ForEach body return success
   instantly and do nothing; (c) an in-flight ForEach does not survive a restart. **Postgres only.**
3. `fuse-engine-researcher` — replay reconstruction for `foreach:*` spans the aggregate, the actor and
   the thread model; the planner would otherwise guess.
4. `fuse-implementation-planner` → `fuse-go-implementer` → `fuse-code-reviewer`.

If the real fix is large, the backlog explicitly sanctions the interim: **schema validation that
rejects `system/*` inside a ForEach body**. That is a legitimate scope for this id, not a lesser
outcome — but state it as the chosen scope rather than drifting into it.

## Out of scope

- **A-02** owns replaying `subworkflow:started`/`awakeable:created`/`sleep:started`. Same class of bug,
  different id — do not bundle.
- **V-c** owns the unguarded `graph.FindNode` nil-deref at `workflow.go:312-314` — a distinct line from
  the ForEach one at `:310-311`. Reconstructing the threads removes *a* way to reach it; do not fix V-c.
- **C-12** owns multi-thread resume. **F-02** owns the harness. **A-07** owns replay's duplicate
  appends, which any new replay handler must not reintroduce.
- Do not add ForEach features (concurrency limits, ordering guarantees) while fixing durability.

## Decisions

Probably **neither** an ADR nor a SpecKit spec — a durability defect plus a migration. It tips to an
**ADR** only if the fix changes the ForEach threading model itself, in which case **ADR-0011 · Thread
model for fork/join and ForEach** needs an amendment or a superseding ADR rather than a silent code
change. Also interacts with **ADR-0010 · Durable execution via an append-only journal** (adding read
sites for four write-only entry types) and **ADR-0003 · In-memory repositories by default** (the memory
driver will not catch the enum violation at all — a green memory test proves nothing here).
