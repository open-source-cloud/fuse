## What the backlog says

> Minted in-engine, written only into a journal entry's `Data` map. `GET /v1/workflows/{id}` returns
> `{workflowId, status}`; `SnapshotTimelineEvent` drops `Data`; snapshot and trace persist only at
> terminal state. `AwakeableRepository.FindPending(workflowID)` exists with no route in
> `mux_worker.go`. A caller cannot learn the ID it must call back with — a documented feature no
> external caller can use.

## Premise status

**READ-confirmed; UNVERIFIED by execution.** Every clause was re-read while writing this dossier or is
recorded in the packs:

- `AwakeableRepository.FindPending(workflowID string) ([]*workflow.Awakeable, error)` is declared at
  `internal/repositories/awakeable.go:16` and implemented by **both** drivers — with **no production
  caller**, only the implementations and their tests. Re-confirmed by reading.
- The id exists only in a journal entry's `Data` map (`workflow_handler.go:782`).
  `SnapshotTimelineEvent` (`internal/workflow/execution_snapshot.go:47`) has no `Data` field;
  `BuildTrace` handles only `step:*` and `state:changed` (`trace_builder.go:22-68`); snapshot and trace
  persist only from `sendWorkflowCompleted` (`workflow_handler.go:518-519`), i.e. at terminal state.
- `GET /v1/workflows/{workflowID}` (`mux_worker.go:220`) returns `dtos.GetWorkflowResponse` —
  `{workflowId, status}` and nothing else. Note the backlog's own text says `GET /v1/workflows/{id}`;
  there is **no** `/status` route, whatever older prose says. Trust `mux_worker.go`.

Stage 1 here is a 15-minute confirmation, not an investigation: assert that no route returns a pending
gate's id. The test that proves it is also the first (failing) commit of the fix, because it becomes
the new route's test.

## Route

1. `fuse-premise-verifier` — narrow: no route exposes a pending awakeable id; `FindPending` has no
   production caller. Cheap, and it produces the first failing commit.
2. `fuse-implementation-planner` — the design question is small but real: a new route
   (`GET /v1/workflows/{id}/awakeables`?) versus extending `GetWorkflowResponse` versus folding it into
   **C-09**'s state read model. Decide deliberately; do not let it default.
3. `fuse-go-implementer` → `fuse-code-reviewer`.

No researcher stage — a single handler plus a route in a table the pack already maps.

## Out of scope

- **C-09** owns the mid-flight run read model (thread positions, completed steps, pending steps, open
  gates). If C-09 lands first, C-07 is a field in its response — coordinate on ordering rather than
  building two overlapping surfaces. Do not build the state endpoint here.
- **C-05** owns the typed gate payload. Expose the **id**; do not design what the gate carries.
- **C-06** owns deadlines and the sweeper. Do not add expiry handling to this route.
- Do not add `Data` to `SnapshotTimelineEvent` as a drive-by — that widens the snapshot contract and
  belongs with C-09.

## Decisions

**Neither an ADR nor a SpecKit spec** — an ordinary plumbing task, and the query already exists.
Interacts with **ADR-0010 · Durable execution via an append-only journal** (the id lives in a journal
entry's `Data`) and the awakeable half of the gate story that **C-05** will formalise.

This is a **public HTTP API addition**: the changelog rule applies and **there is no CHANGELOG file in
this repo** — raise it with the maintainer rather than inventing a destination.
