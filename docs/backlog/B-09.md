## What the backlog says

> Children spawn through the same `WorkflowSupervisorName` route as any run — no depth counter, no
> ancestry check, no cycle detection. A self-referencing schema is an unbounded fork bomb. Once agents
> compose workflows from data, this becomes triggerable **by model output**, not by a badly written
> schema. Depth counter in `SubWorkflowRef`, configurable max, ancestry cycle detection at spawn.

## Premise status

**UNVERIFIED as a runtime consequence — stage 1 must run `fuse-premise-verifier` before any code.**
Nobody has executed a self-referencing schema and observed unbounded spawning.

The structural half was **READ** during dossier creation and holds exactly as the entry states:
`internal/workflow/subworkflow.go` declares `SubWorkflowRef` with six fields —
`ParentWorkflowID, ParentThreadID, ParentExecID, ChildWorkflowID, ChildSchemaID, Async` — and **no depth
or ancestry field**; and `handleSubWorkflowAction` (`internal/actors/workflow_handler.go:901`) sends the
child's trigger to `gen.Atom(actornames.WorkflowSupervisorName)` at `:930`, the same route any run takes.
There is no guard between those two points.

The verifier's target is the consequence, not the absence: a schema whose node spawns itself should
produce children without bound. Note the async/sync split matters here as it did for F-01.2 — with
`async=true` the parent does not wait, so the fan-out shape differs.

## Route

Standard pipeline; nothing about this task inverts it.

1. `fuse-premise-verifier` — reproduce unbounded spawning from a self-referencing schema. Ask it to
   state whether the sync and async paths differ, and to bound the test so a fork bomb does not take the
   suite with it.
2. `fuse-implementation-planner` — with the verdict. It must decide whether depth is carried in-process,
   persisted on `SubWorkflowRef`, or both, and say which; persisting it means a migration, so load
   `persistence-and-migrations` for the idiom at that point.
3. `fuse-go-implementer` → `fuse-code-reviewer`.

## Done when

Derived from the task text; the backlog gives no "Done when" list.

- [ ] A depth counter exists on `SubWorkflowRef` and is propagated parent → child at spawn.
- [ ] The maximum depth is configurable, with a sane default, and a violation is refused **before** the child is spawned.
- [ ] Ancestry cycle detection at spawn catches a self-referencing schema even below the depth limit.
- [ ] Exceeding either limit fails the run with a distinguishable error, not a generic `FunctionError` and not a panic.
- [ ] Driver parity: memory and Postgres agree, with a migration if `sub_workflow_refs` gains a column.
- [ ] A reproducing test lands first, failing, in the first commit; it is bounded so a regression cannot exhaust CI.
- [ ] `make lint && make build && make test` green; `make test-functional` with `DB_POSTGRES_DSN` exported.

## Decisions

**Probably neither an ADR nor a SpecKit spec** — this is a bounded safety guard on an existing
mechanism. **ADR-0032** (Sub-workflow composition: child workflows as first-class instances, Accepted)
governs the composition contract; if the depth/ancestry rule materially changes that contract, it is a
**new** ADR (0032 is Accepted and therefore immutable), next free number **0035**. Also interacts with
**ADR-0016** (Multi-scope concurrency control and rate limiting) and **ADR-0022** (retry and
error-handling model — a depth violation must not be retried into the same wall).

A new config variable is user-visible surface; document it where the other `Config` knobs are documented.
