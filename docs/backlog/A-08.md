## What the backlog says

> Automatic retries reuse the same `ExecID` (`HandleNodeFailure → RetryFunctionAction{
> RunFunctionAction{FunctionExecID: execID}}`); attempts are separable only via `step:retrying` and the
> in-memory `RetryTracker`, not rebuilt on replay. Manual retry does it right (`RetryNode` mints a fresh
> ExecID, records `previousExecId`).
>
> Add an attempt counter to the journal entry and rebuild `RetryTracker` on replay. Cost attribution per
> attempt (C-04) and the trace view both need it, and remote nodes make retries far more common.

## Premise status

UNVERIFIED — stage 1 must run `fuse-premise-verifier` before any code. Nobody has executed a test
showing that a run which retried before a crash loses its attempt bookkeeping on resume, or that two
attempts of one exec id are indistinguishable in the persisted trace.

Same class of defect as A-02 and C-08: state that lives only in a plain in-memory structure and is never
reconstructed from the journal. The pack `durable-execution-internals` carries the replay control flow
and the list of which entry types are actually read.

## Route

Standard pipeline, no inversion.

1. `fuse-premise-verifier` — sub-claims: (i) automatic retry reuses the exec id; (ii) `RetryTracker` is
   not rebuilt on replay, so a resumed run's retry budget/attempt index is wrong; (iii) two attempts of
   one exec id are indistinguishable in the persisted trace.
2. `fuse-implementation-planner` — with the verdict. Must state whether the counter is a field on an
   existing entry or a new entry type, and therefore whether a migration is needed.
3. `fuse-go-implementer`, then `fuse-code-reviewer`.

If the plan adds a **new** `JournalEntryType`, read the C-08 trap first: `migrations/
000001_create_tables.up.sql:12` creates `journal_entry_type` with 13 values against 18 declared in Go,
and the only widening since is `000004`. A missing enum value makes a Postgres journal flush fail.

## Done when

Derived; the backlog gives no "Done when" list.

- [ ] Journal entries for a retried step carry an attempt number.
- [ ] `RetryTracker` is rebuilt from the journal on replay, so a resumed run's retry budget matches an
      equivalent run that never crashed.
- [ ] Two attempts of the same exec id are separable in the persisted trace.
- [ ] Manual retry (`RetryNode`) keeps working unchanged, including `previousExecId`.
- [ ] Verified under `DB_DRIVER=postgres`, with any enum widening shipped as a migration.
- [ ] `make lint && make build && make test` green.

## Out of scope

- **C-04** consumes this for per-attempt cost attribution. Do not add GenAI attributes here.
- **C-10** derives a per-node idempotency key from `(runID, execID, attempt)`. That the `attempt`
  component must come from A-08 is *inference*, not a backlog-declared dependency — do not design C-10's
  key format inside this task.
- **A-07** owns duplicate journal appends on replay. **A-03** owns the delivery guarantee that makes
  retries safe across a restart. **A-02** owns the intercepted system types.

## Decisions

Neither an ADR nor a SpecKit spec, unless the plan changes the retry *model* rather than its
bookkeeping. Interacts with **ADR-0022** (Retry and error-handling model) — `Accepted`, so a change to
the model itself is a new ADR — and with **ADR-0010** (Durable execution via an append-only journal),
which is the record for what replay reconstructs. The trace it improves is **ADR-0020**'s. If a
migration ships, it needs a migration path; there is no CHANGELOG file in this repo.
