## What the backlog says

> Sleeps, awakeable timeouts and workflow timeouts are per-actor `SendAfter` — lost on restart, with
> no sweeper (the only periodic actors are `workflow_claim_actor.go` and `cron_scheduler.go`). A
> 72-hour gate that outlives a deploy has no deadline. The `Awakeable` row already carries
> `DeadlineAt`. Periodic sweep for expired pending awakeables and sleeps, re-arm live timers on boot,
> claim-aware so two nodes do not fire the same timeout.

## Premise status

**UNVERIFIED by execution — stage 1 must run `fuse-premise-verifier` before any code.** This is a
defect, not a proposal: the timers exist and die with the process.

READ-confirmed supporting facts, from `durable-execution-internals` and
`capability-registry-and-agents`:

- `startWorkflowTimeout` is called **only** on the fresh-create path (`workflow_handler.go:193`) and
  **not** on the resume path (`Init`, around `:143`) — so a schema's total timeout is silently lost
  after **any** restart, not merely delayed. The backlog does not say this; it is worth its own
  assertion.
- ⚠️ `DeadlineAt` is **always set** — `workflow_handler.go:775` is `DeadlineAt: now.Add(action.Timeout)`
  — so a gate created with no timeout gets `DeadlineAt == CreatedAt`. **A sweeper treating
  `deadline_at <= now()` as expired would kill every untimed gate on its first pass.** This is the
  single most dangerous trap in the task.
- ⚠️ `AwakeableTimedOut` and `AwakeableCancelled` are declared and **never assigned** in production
  code; the only runtime `timedOut` value is the literal `false` at `workflow_handler.go:845`. A
  timed-out gate today becomes a generic `FunctionError{"execution timeout exceeded"}` via
  `handleMsgTimeout` (`:551`) and the row stays `pending` forever. A sweeper needs a terminal state
  that does not exist yet.
- A restart with a pending `system/sleep` re-arms the **full** original duration
  (`workflow_handler.go:710-763`) — a 24h sleep with 10 minutes left restarts at 24h. The remainder is
  computable: `sleep:started` persists both `Timestamp` and `Data["duration"]`. **That clause belongs
  to A-02**; C-06 owns the sweeper and the boot-time re-arm, not the replay handler.

## Route

1. `fuse-premise-verifier` — three sub-claims, each its own assertion: (a) a pending awakeable's
   deadline is not enforced after a restart; (b) `startWorkflowTimeout` is not called on the resume
   path, so the workflow timeout is lost entirely; (c) a no-timeout gate has `DeadlineAt == CreatedAt`.
   Postgres only — a memory-driver result proves nothing about resume.
2. `fuse-engine-researcher` — the sweep spans actors, repositories and the HA claim layer, so the
   planner would otherwise guess. Ask specifically: what terminal state an expired gate should take,
   given `AwakeableTimedOut` is never assigned today.
3. `fuse-implementation-planner` → `fuse-go-implementer` → `fuse-code-reviewer`.

The F-02 harness's "kill with a pending `system/sleep`" and pending-awakeable scenarios are the
regression bed; coordinate rather than building a second rig.

## Done when

Derived; the backlog gives no "Done when".

- [ ] A failing test lands first showing a deadline lost across a restart.
- [ ] A periodic sweeper finds expired pending awakeables and sleeps **without** touching untimed
      gates — asserted explicitly against the `DeadlineAt == CreatedAt` case.
- [ ] Live timers are re-armed on boot, including the workflow timeout on the resume path.
- [ ] The sweep is claim-aware: two nodes do not fire the same timeout. Verified with
      `HA_ENABLED=true` and `DB_DRIVER=postgres` — the memory claim repository is a no-op.
- [ ] An expired gate reaches a distinguishable terminal state, not a generic execution-timeout error.
- [ ] `DB_POSTGRES_DSN=... make test-functional` green; `go test -race ./internal/... ./pkg/...` green
      (this is actor and timer work; race is not in any gate).

## Out of scope

- **A-02** owns replaying `sleep:started`/`awakeable:created` and the "restart re-arms the full
  duration" defect. C-06 owns the sweeper and the boot-time re-arm; do not fix A-02's replay handler
  here even though the files touch.
- **C-07** owns exposing awakeable ids. **C-05** owns the gate payload and its state transitions —
  including, arguably, what "expired" means to a caller; coordinate on the terminal state rather than
  inventing two.
- **C-11** owns the claim-fails-open defect in `claimForThisNode`. A claim-aware sweeper inherits that
  bug; note it, do not fix it.
- Do not widen `FindPending` into a general query surface beyond what the sweeper needs.

## Decisions

Probably **neither** an ADR nor a SpecKit spec — this is a durability defect with a known shape. Two
things could tip it to an ADR: introducing a **new terminal awakeable state** (a persisted-state
change), and choosing sweep ownership under HA. Interacts with **ADR-0023 · Timeout enforcement via
actor timers** (the decision that made every deadline in-memory — if C-06 changes that, ADR-0023 needs
an amendment or a superseding ADR, not a silent code change), **ADR-0018 · High availability: claims,
clustering, schema replication** (lease semantics the sweep must respect), and **ADR-0010 · Durable
execution via an append-only journal**. Next free ADR number is **0035**.
