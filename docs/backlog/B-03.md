## What the backlog says

> One registration produces two projections: a **node** usable in a graph, and a **tool** usable by an
> agent. Single definition, single schema, single auth config, single version. Registration via API and
> via schema-as-code.
>
> Design constraint for the ADR: an agent calling a capability directly and a workflow node calling the
> same capability must produce the same journal entries, the same span shape, and the same idempotency
> behaviour. If the two paths diverge, traceability becomes conditional on which one was used — and that
> is the property Enterprise is sold on.

## Premise status

**net-new — there is no registry to fix.** `internal/packages/registry.go` is a function registry, and
`internal/packages/agent_tools.go` is an *adapter over the same registry*, not a second projection.

**The parity constraint does not hold today.** V-a (recorded unfiled in
BACKLOG_V2.md, 2026-08-11, **read from control flow — not executed**): `internal/packages/agent_tools.go:86`
(`InvokeTool`) calls `LoadedPackage.ExecuteFunctionSync` (`internal/packages/loaded_package.go:50`),
which goes straight to the transport and never enters `internal/actors/workflow_func.go` — the **only**
creator of the `node.execute` span (`:90`) and the only caller of `recordNodeDuration` (`:181`). So an
agent tool call emits no span, no `fuse_node_exec_duration_seconds` sample, and (per the
`capability-registry-and-agents` parity table) no `step:*` journal entry, no retry policy and no
timeout. The only durable record of a tool call is the opaque `steps` array inside the agent node's
single `FunctionOutput`.

**This is direct evidence for B-03's design constraint**, and it is the reason the constraint has to be
designed in rather than assumed. Stage 1's job is narrow: upgrade V-a from *read* to *executed*.

⚠️ **Trap that will bite the registry predicate.** `MapToRegistryPackage` hardcodes
`Transport: transport.Internal` (`internal/packages/loaded_package.go:70`), so
`packages.FunctionMetadata.Transport` is *always* `"internal"` and the second clause of `isExposableTool`
(`internal/packages/agent_tools.go:101`) is vacuously true. The only working discriminator is
`LoadedFunction.Transport == nil`. Any B-03 predicate written against `Metadata.Transport` matches
everything.

## Route

**Blocked on B-01** — a capability's declaration and versioning clauses are B-01 decisions 7 and 8.

1. `fuse-premise-verifier` — **narrow**: execute V-a's claim (an agent tool call produces no
   `node.execute` span, no `step:*` journal entry, no `fuse_node_exec_duration_seconds` sample) so the
   ADR rests on an executed fact rather than a read. The routing table asks for exactly this: "VERIFY the
   projection-parity premise against `agent_tools.go` first".
2. `fuse-protocol-spec-author` — only if the registry needs a clause B-01 did not settle (declaration
   shape, capability versioning, per-capability auth config). A spec revision, never Go.
3. `write-adr` — **before any code**; the planner's decision table names "B-03 registry" as ADR-class.
4. `fuse-implementation-planner` → `fuse-go-implementer` → `fuse-code-reviewer`.

## Done when

Derived from the task text; the backlog gives no "Done when" list.

- [ ] One registration produces both projections, carrying a single schema, auth config and version — registering the same endpoint twice, once per consumer, is impossible by construction.
- [ ] Registration works via API **and** via schema-as-code.
- [ ] An agent invoking a capability and a graph node invoking the same capability produce the **same journal entries** — asserted, not argued.
- [ ] The same **span shape** — asserted against a real OTel provider, in the shape F-01.1 used.
- [ ] The same **idempotency behaviour**.
- [ ] The eligibility predicate does not key on `Metadata.Transport` (vacuously `internal` for everything).
- [ ] The ADR records the projection model and is landed before implementation code.
- [ ] `make lint && make build && make test` green.

## Out of scope

- **V-a itself is not fixed here.** It is unfiled by design; B-03 *uses* it as evidence. If closing the
  parity gap for existing `ai/*` tools falls out of the registry work, that is C-01's scope, not a
  drive-by.
- **C-01** owns binding `ai/agent`/`ai/chat` to registry capabilities.
- **B-04** owns MCP ingestion; do not design the registry around MCP specifics.
- **B-02** owns the transport a remote capability dispatches over. **B-08** owns worker lifecycle.
- **A-11** owns per-execution addressing of node output; the agent-loop overwrite problem is not solved here.
- The `ai` package exclusion and the `interceptedOrAsyncFunctionIDs` denylist are today's tool-catalog
  policy — changing what an agent may call is C-01/C-05 territory.

## Decisions

**ADR required, before code** — the planner's decision table names the registry explicitly, and the
backlog states the parity requirement as a "design constraint for the ADR". Next free number is **0035**
(coordinate with A-03, A-04, A-05, A-09, A-11, B-01). A **SpecKit spec is defensible too** — "a whole
capability registry" is the planner table's own example of SpecKit-class work — but note SpecKit's
`NNN-short-name` branch naming conflicts with the `feat/`/`fix/` prefixes; the maintainer decides.

Interacts with **ADR-0024** (Function packages: registry with declarative metadata), **ADR-0007** (Agent
reasoning loop & tools-from-functions), **ADR-0027** (Async tool invocation via a sub-execution channel,
Proposed — its `ExecRuntime` port is one way to reach parity) and **ADR-0017** (idempotency is
trigger-level only).

Registration is public API; the changelog rule applies and **there is no CHANGELOG file in this repo** —
raise it rather than inventing one.
