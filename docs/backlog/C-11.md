The cheapest correctness fix in Tier C, on the HA split-brain path.

## What the backlog says

> `claimForThisNode` returns `true` on a claim-store error and runs the workflow anyway. Under
> Postgres pressure that is a split-brain path with side effects. Fail closed, log, retry next sweep.
> Also revisit `ClaimWorkflows(nodeID, 10)` every 5s — recovering 50 runs after a node loss takes ~25
> seconds.

## Premise status

**Clause 1 is a CONFIRMED code fact, re-read while writing this dossier.** The behaviour is not
accidental — it is documented in the function's own comment:

```go
// ... On a claim-store error it fails open (runs)
// rather than dropping the workflow.
func (a *WorkflowHandler) claimForThisNode(wfID workflow.ID) bool {
	owned, err := a.claimRepo.ClaimWorkflow(resolveNodeID(a.config), wfID.String())
	if err != nil {
		a.Log().Error("failed to claim workflow %s (running anyway): %s", wfID, err)
		return true
	}
```

`internal/actors/workflow_handler.go:360-372`. Because it is a deliberate, documented choice, the fix
is a **decision reversal**, not a bug repair — say so in the PR body.

**The consequence — two nodes running one workflow with real side effects — is UNVERIFIED.** Stage 1
owes an executed reproduction: a claim repository that returns an error, and an assertion that the
handler proceeds into the run anyway. Clause 2 (batch size and sweep interval) is arithmetic over
`ClaimWorkflows(nodeID, 10)` every 5s and needs no reproduction, only a decision.

## Route

1. `fuse-premise-verifier` — an erroring claim repository, and the assertion that the run proceeds.
   Needs `HA_ENABLED=true` and `DB_DRIVER=postgres` to be meaningful.
2. `fuse-implementation-planner` — small, but it must decide what "retry next sweep" means concretely:
   which actor re-drives the workflow after a failed claim, and whether a failed claim leaves the run
   discoverable by `ClaimWorkflows` on the next pass.
3. `fuse-go-implementer` → `fuse-code-reviewer`.

No researcher stage — the control flow is fully mapped in `durable-execution-internals`.

## Done when

Derived; the backlog gives no "Done when".

- [ ] A failing test lands first: on a claim-store error the workflow currently runs anyway.
- [ ] On a claim-store error the handler **fails closed** — it does not run the workflow, it logs, and
      it leaves persisted state untouched so the next sweep can retry.
- [ ] The run is provably picked up on a subsequent sweep; failing closed must not mean losing the run.
- [ ] Clause 2 is answered: `ClaimWorkflows(nodeID, 10)` every 5s is either made configurable, widened,
      or explicitly left alone **with the reason written down**.
- [ ] Verified with `HA_ENABLED=true` and `DB_DRIVER=postgres`; a green memory-driver test proves
      nothing here (the memory claim repository is a no-op).
- [ ] `go test -race ./internal/... ./pkg/...` green — this is actor and concurrency work, and race is
      not in any gate.

## Decisions

**Neither an ADR nor a SpecKit spec** — one branch, and the reversal of a documented default. But the
default is documented in a comment that cites **ADR-0018 · High availability: claims, clustering, schema
replication**: check whether ADR-0018 records the fail-open choice as a decision, and if it does, that
ADR needs an amendment or a superseding ADR rather than a silent code change. Also touches **ADR-0003 ·
In-memory repositories by default** (the no-op memory claim repo is why this cannot be tested under
memory).
