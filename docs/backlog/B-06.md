## What the backlog says

> Two entry points from one core: plain function registration for scripts and serverless, and NestJS
> decorators for the framework case. The decorator marks a handler, the SDK exposes the route, handles
> ack/async/callback and idempotency, and completes when the handler resolves — so a customer writes an
> ordinary async method and gets durable orchestration.
>
> Ship with a working example that survives an engine restart mid-call. That example is the README.

## Premise status

**net-new, and built outside `core/`.** There is nothing in this repository to verify, reproduce or
extend. The two inputs are B-01's published spec and B-05's conformance suite; both are open.

The engine-side reality the SDK is written against: FUSE declares `HTTP` and `gRPC` in
`pkg/transport/type.go` and implements neither, and an API-registered function is metadata-only
(`internal/packages/loaded_package.go:41` — `function %s has no transport`). Until **B-02** lands there
is no engine behaviour for an SDK to talk to. Do not start the SDK to "prove out" the protocol; that is
what B-05 is for.

## Route

**Blocked on B-02 and B-05.** Neither has started.

No pipeline agent in this repo writes TypeScript: `fuse-go-implementer` is Go-only and
`fuse-e2e-harness-engineer` builds Go harnesses. The SDK is written by a contributor outside this
pipeline. What the pipeline owns is the spec side:

1. `fuse-protocol-spec-author` — hand it the SDK's open questions. Every ambiguity an SDK author hits is
   a spec defect: it returns a versioned clause revision, not an SDK workaround. It writes Markdown only.
2. The SDK author implements against the revised spec, outside this repo.
3. B-05's suite is the review gate. If an engine behaviour is missing, file a backlog task against Core
   with the clause id attached — **do not patch the engine from the SDK's side**.

## Done when

Derived from the task text; the backlog gives no "Done when" list.

- [ ] One core, two entry points: plain function registration (scripts, serverless) and NestJS decorators.
- [ ] The decorator marks a handler and the SDK exposes the route; the customer writes an ordinary async method.
- [ ] The SDK handles ack (sync vs `202`), the async callback, and idempotency, per the B-01 clauses.
- [ ] A handler that resolves completes the step; a handler that throws maps onto the B-01 completion taxonomy (business vs infrastructure error) rather than one generic failure.
- [ ] The full B-05 conformance suite passes against it, unmodified.
- [ ] A working example survives an engine restart mid-call — and that example is the README.
- [ ] Every SDK behaviour cites the spec clause id it implements.

## Out of scope

- **Engine changes of any kind.** B-02 owns the transport, B-08 owns worker lifecycle, A-04 owns trace
  context. A gap found while building the SDK is a filed backlog task, not a patch.
- **B-07** (PHP / Laravel) — same contract, separate task, separate PR. Do not generalise the two into a
  shared abstraction before both exist.
- **B-05** — the suite is a prerequisite, not part of this task. "Build before the first SDK" is explicit.
- **Protocol changes.** A missing or ambiguous clause is a versioned spec revision by
  `fuse-protocol-spec-author`; an SDK-local workaround silently forks the protocol.

## Decisions

**No ADR in `core/`.** Decisions about the SDK's own architecture belong to its repository. B-01's ADR is
the decision record for everything on the wire.

Interacts with the backlog rule that "the protocol spec is a contract. Once B-01 is published and an SDK
exists, changing it breaks strangers" — this task is the moment that rule starts to bind. It also makes
the missing changelog concrete: **there is no CHANGELOG file in this repo**, so a spec revision has no
documented destination yet; raise it with the maintainer.
