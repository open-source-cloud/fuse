## What the backlog says

> `dtos.TriggerWorkflowRequest` is `{schemaID, idempotencyKey, environment}` — no payload. Plumbing is
> built and dropped: `TriggerWorkflowMessage.Input` exists, `NewTriggerWorkflowWithInputMessage` exists,
> webhook/cron/event populate it — but `spawnWorkflowActor` takes three args, `WorkflowHandlerInitArgs`
> has three fields, and `Trigger` hardcodes `Args: map[string]any{}`.
>
> Thread it end to end and expose it to `SourceFlow` under a reserved key (`trigger.*`).
>
> **Elevated in this design:** when an agent composes a workflow run, parameterising the trigger *is* the
> composition mechanism. Without it the agent has no way to pass anything into what it starts.

## Premise status

UNVERIFIED as a defect narrative — stage 1 must run `fuse-premise-verifier` before any code. Every
structural fact the entry cites was READ during dossier creation and holds exactly as written (see Code
area). Nobody has EXECUTED a test showing a caller-supplied payload is dropped end to end, and the
`trigger.*` exposure is net-new behaviour with nothing to reproduce.

## Out of scope

- **B-10** owns passing input into sub-workflows. `handleSubWorkflowAction` journals an input and then
  sends `NewTriggerWorkflowWithEnvMessage` (`internal/actors/workflow_handler.go:929`), dropping it —
  that line is B-10's, not this task's.
- **A-11** owns per-execution addressing of node output. `trigger.*` is a reserved *input* namespace,
  not a re-keying of `aggregatedOutput`.
- **A-09** owns payload size. A large trigger payload externalizes like any other; add no threshold here.

## Decisions

Neither an ADR nor a SpecKit spec, most likely — this is plumbing. Interacts with **ADR-0004**
(Multi-trigger workflow initiation) and **ADR-0013** (Workflow schema model and edge-based input
mapping); both are `Accepted` and therefore immutable, so if the `trigger.*` namespace changes the
input-mapping model the planner should propose a follow-up ADR (next free number 0035) rather than
editing 0013. Public HTTP contract change → the backlog's "changelog entry and a migration path" rule
applies, but **there is no CHANGELOG file in this repo**; raise it with the maintainer instead of
inventing one.
